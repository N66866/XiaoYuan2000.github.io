# Prompt Engineering

# 本章导读

Prompt Engineering 关注如何把任务、上下文、约束和输出格式清楚地交给模型。它不是“咒语”，而是把模糊需求变成可执行指令的工程方法。

在真实项目里，Prompt 不是随便写一句“帮我分析一下”，而是要像接口设计一样明确输入、输出、边界和异常情况。一个好的 Prompt，应该让模型知道：

  • 它现在扮演什么角色。
  • 需要完成什么任务。
  • 可以参考哪些上下文。
  • 必须遵守哪些约束。
  • 最终结果要长什么样。

# 如何设计 Prompt

# 明确角色设定

角色设定用于告诉模型：它应该站在什么专业身份、语气和知识背景下完成任务。

例如：

# 角色
你是一名网络安全专家，请根据以下安全告警日志，输出专业分析报告。
1
2

角色不是装饰，它会影响模型的表达风格、关注重点和回答深度。比如同样分析一段日志，网络安全专家会关注攻击类型、风险等级、影响范围和处置建议；普通助手可能只会做表面总结。

常见角色包括：

  • Java 架构师
  • 代码审查专家
  • 网络安全专家
  • 产品经理
  • 法律顾问
  • 数据分析师
  • 面试官
  • 教学助教

# 给出清晰具体的任务指令

Prompt 要避免模糊、笼统和过度客气。模型需要明确知道“做什么、怎么做、做到什么程度”。

不好的写法：

写一篇文章。
1

更好的写法：

撰写一篇 800 字左右的文章，主题是“人工智能在医疗领域的应用”。
要求条理清晰、语言通俗，适合发布在技术公众号。
1
2

工程里可以多使用明确的约束词，例如“必须”“只允许”“不要”“按照以下格式”。这不是为了语气强硬，而是为了减少模型自由发挥空间。

可以记住一个原则：

Prompt 越模糊，模型越自由；Prompt 越具体，输出越可控。

# 使用结构化 Prompt

结构化 Prompt 是把角色、任务、背景、要求、输出格式拆成明确模块，让模型更容易理解任务边界。

常见结构：

# 角色
你是一名资深的市场文案撰写专家。

# 任务
撰写一份产品描述。

# 要求
1. 强调产品的独特卖点。
2. 使用简洁明了的语言。
3. 字数控制在 150 字以内。
4. 风格专业且有吸引力。

# 输出格式
- 标题：一句话概括产品卖点。
- 正文：2-3 句描述产品特性和优势。
- 列表：用项目符号列出 3 个核心特点。

结构化 Prompt 的好处是：

  • 模型更容易识别任务重点。
  • 多步骤任务更不容易遗漏要求。
  • 输出格式更稳定。
  • 后续维护时更容易修改某一块内容。

在复杂业务中，Prompt 可以按模块拆成：

  • Role：角色。
  • Task：任务。
  • Context：上下文。
  • Constraint：约束。
  • Output：输出格式。
  • Examples：示例。

# 结构化 Prompt 框架

所谓结构化 Prompt 框架，本质上是一组 Prompt Templates。它们不是必须死记的标准，而是帮助我们把需求拆成清晰模块，让模型更好理解角色、任务、背景、约束和输出格式。

不同框架名字很多，但底层都绕不开几个核心要素：

  • 角色定位：模型以什么身份回答。
  • 任务目标：模型要完成什么。
  • 上下文背景：模型可以参考什么信息。
  • 约束边界：模型应该做什么、不应该做什么。
  • 输出格式：结果应该长什么样。

# RTF：Role、Task、Format

RTF 是最基础的提示词模板，适合通用任务和简单任务。

结构：

  • Role：角色，定义模型身份或专业背景。
  • Task：任务，说明要完成的具体目标。
  • Format：格式，指定输出形式、风格或语气。

示例：

# Role
你是一名资深市场分析师。

# Task
请分析当前中国新能源汽车市场的发展趋势，指出未来三年的主要增长点。

# Format
请以 Markdown 表格形式输出，包含“趋势”、“原因”、“预测增长率”三列。

# ICIO：Instruction、Context、Input、Output

ICIO 强调把指令、上下文、输入和输出拆开，适合需要背景理解或多阶段处理的任务。

结构：

  • Instruction：核心任务指令。
  • Context：背景信息和辅助说明。
  • Input：具体要处理的文本或数据。
  • Output：结果格式和表达要求。

示例：

# Instruction
请为指定产品生成一段简短、有吸引力的营销文案。

# Context
你是一名资深品牌营销文案策划，擅长为电商产品撰写高转化率广告语。
目标受众是年轻、注重品质的都市白领。

# Input
产品名称：AI 健康监测手环
产品特点：实时监测、血压血氧测量、睡眠监测、外观简约、佩戴轻盈。

# Output
请输出一段不超过 100 字的营销文案，使用 Markdown 格式，语言简洁、有节奏感。

# CRISPE：更强调能力、洞察和风格

CRISPE 适合需要角色深度、专业视角和创意表达的任务，例如学术写作、科研分析、市场策略和内容创作。

结构：

  • Capacity：能力边界，说明模型擅长什么。
  • Role：身份定位。
  • Insight：背景信息、知识视角或洞察点。
  • Statement：具体任务目标。
  • Personality：语气、风格和表达个性。
  • Experiment：探索性要求，例如生成多个方案、提出假设。

示例：

# Capacity and Role
你是一名资深市场策略分析师，擅长品牌定位与消费趋势洞察。

# Insight
某科技品牌计划推出一款主打 AI 功能的智能手表，目标群体为 25-40 岁城市白领。

# Statement
请撰写一份市场策略分析报告，包含市场格局、用户画像、差异化定位和推广策略。

# Personality
请以专业咨询顾问的语气撰写，逻辑清晰、数据导向，避免空泛表达。

# Experiment
在结尾提供一个创新性市场假设，并说明商业价值和潜在风险。

# CO-STAR：适合复杂目标和明确受众

CO-STAR 用于明确背景、目标、范围、语气、受众和响应形式。它适合企业报告、课程设计、市场策略分析、活动策划等中等复杂度任务。

结构：

  • Context：背景，说明为什么做。
  • Objective：目标，说明要达成什么。
  • Scope：范围，限定内容边界。
  • Tone：语气，控制表达风格。
  • Audience：受众，说明写给谁看。
  • Response：响应形式，规定输出结构。

示例：

# Context
近年来青少年沉迷社交媒体、遭遇网络不良信息的问题频发，学校计划开展主题教育活动。

# Objective
帮助青少年理解合理使用社交媒体的重要性，并提供可操作建议。

# Scope
聚焦 13-17 岁青少年，涵盖使用时长管理、信息辨别、隐私保护 3 个方面。

# Tone
亲切、鼓励，像学长学姐的建议，避免说教。

# Audience
初中至高中阶段学生。

# Response
分点列出 5 条具体建议，每条配一个简短案例或比喻。

# TIDD-EC：适合规则强、禁区明确的任务

TIDD-EC 适合需要明确指导、允许行为和禁止行为的任务，例如教育培训、法律咨询、技术支持、客服合规回复等。

结构：

  • Task Type：任务类型。
  • Instructions：执行指令。
  • Do：应该做什么。
  • Don’t：禁止做什么。
  • Example：示例。
  • Content：用户内容或背景数据。

示例：

# 任务
撰写法律意见书。

# 指令
根据客户提供的案件信息，分析法律风险并提出可行建议。

# 你应该做
- 结合相关法律法规进行分析。
- 条理清晰地列出风险点。
- 提供操作性建议。

# 你禁止做
- 不要提供具体诉讼策略或个案判决。
- 避免主观推测，确保内容专业客观。

# 示例
客户希望了解合同条款中的潜在风险，应指出关键条款可能存在的履约争议，并建议完善合同条款或加强证据准备。

# 用户内容
- 案件类型：商业合同纠纷
- 关键条款：付款条款、违约责任、交付时间

# BROKE：适合目标导向和持续优化

BROKE 适合活动策划、产品设计、内容创作、运营方案等需要目标、衡量标准和后续迭代的任务。

结构：

  • Background：背景。
  • Role：角色。
  • Objective：目标。
  • Key Result：关键结果或衡量指标。
  • Evolution：改进方向或后续优化。

示例：

# Background
学校希望提高学生环保意识，计划开展一次校园环保主题活动。

# Role
你是校园活动策划师，负责设计活动方案并确保可执行性。

# Objective
通过活动让学生了解环保知识并积极参与实践。

# Key Result
活动结束后，学生参与率达到 80% 以上，提交环保创意作品不少于 50 份。

# Evolution
根据活动反馈调整宣传策略和活动形式，优化互动环节。

# 框架怎么选

不用过度纠结框架名字。可以按任务复杂度选择：

场景 推荐框架 原因
简单通用任务 RTF 角色、任务、格式足够清楚
有明确输入和上下文 ICIO 适合程序模板化拼装
内容创作、策略报告 CRISPE 更强调能力、洞察和风格
面向特定受众的复杂内容 CO-STAR 明确目标、范围、受众和响应
合规、法律、客服、技术支持 TIDD-EC 明确应该做和禁止做
活动策划、产品方案、运营方案 BROKE 有目标、关键结果和迭代方向

真正重要的不是套哪个缩写，而是让 Prompt 结构清晰、任务具体、上下文适量、输出可控。

# Zero-shot 与 Few-shot

# Zero-shot

Zero-shot 是不给模型示例，只通过任务指令让模型完成任务。

示例：

# 任务
判断用户这句话属于什么意图：查询天气、设置提醒、播放音乐。

# 用户输入
帮我查一下明天北京的天气。
1
2
3
4
5

优点：

  • 简洁。
  • 成本低。
  • 适合简单、通用、模型熟悉的任务。

缺点：

  • 复杂任务容易理解偏。
  • 输出格式可能不稳定。
  • 对业务边界不清楚。

比如“查询天气、设置提醒、播放音乐”这类意图很清晰，Zero-shot 通常够用。但如果意图变成“查询 API、检索知识库、联网查询”，模型可能不知道具体边界，这时就需要 Few-shot。

# Few-shot

Few-shot 是在 Prompt 中加入少量输入输出示例，让模型模仿示例的判断逻辑、输出格式和表达风格。

例如，希望模型模仿苹果风格写广告文案，可以给出示例：

# 示例
示例 1：
轻到无感。强到出众。AirPods，让音乐变得更简单。

示例 2：
性能强劲。设计轻盈。全天候陪伴。

示例 3：
突破听觉想象。你的日常，从此不同。

# 当前任务
请模仿以上风格，为矿泉水写一句广告文案。

Few-shot 的价值是让模型“看到你想要的样子”。它特别适合：

  • 意图分类。
  • 固定格式抽取。
  • 风格模仿。
  • 复杂业务规则判断。
  • 多工具路由判断。

缺点是会占用上下文窗口。示例越多，留给用户输入、检索资料和模型输出的空间越少。

# 指定输出格式

如果模型输出要被程序继续处理，必须明确输出格式。不要只说“帮我生成参数”，而要规定字段、类型、枚举值和限制。

示例：

# 任务
你是一个接口参数生成专家，需要根据自然语言描述生成 API 参数配置。

# 输出格式
请只输出 JSON，不要输出多余解释。
字段包括：
- pageSize：每页大小，最大不超过 10。
- pageNum：当前页，默认 1。
- type：类型，0 表示查询商品，1 表示查询订单。

# 用户输入
我想分页查询订单列表。

  • JSON Schema 校验。
  • 字段类型校验。
  • 枚举值校验。
  • 默认值补全。
  • JSON 修复或重试机制。
  • 参数权限和业务规则校验。

LLM 可以生成结构化结果，但最终能不能调用接口，必须由后端代码判断。

# 提供上下文信息

上下文可以帮助模型理解当前任务。常见上下文包括：

  • 用户当前问题。
  • 历史会话。
  • 业务规则。
  • 知识库文档片段。
  • API 文档。
  • 数据库 Schema。
  • 代码文件。
  • 工具返回值。

# 用户问题
[用户问题]

# System Prompt

System Prompt 由系统开发者或应用平台设置，用于约束模型的整体行为。

它通常负责：

  • 设定角色。
  • 设定回答风格。
  • 限制安全边界。
  • 指定默认语言。
  • 规定输出格式。
  • 放置全局业务规则。

特点：

  • 用户通常看不到，也不能直接修改。
  • 会影响整个对话过程。
  • 是应用级默认行为的基础。

# User Prompt

User Prompt 是用户当前输入的问题、指令或请求。

它通常负责：

  • 表达用户当前需求。
  • 提供本次任务的具体上下文。
  • 决定单次交互的内容方向。

工程上要特别注意：用户输入不可信。用户可能输入 Prompt Injection，例如“忽略之前所有规则”。因此系统侧必须把安全规则、权限约束、输出边界放在 System Prompt 和后端校验中，而不能只依赖用户提示词。

# 示例位置也会影响效果

Few-shot 不仅要关注示例内容，还要关注示例放在哪里。

论文 “Where to show Demos in Your Prompt: A Positional Bias of In-Context Learning” 提到：示例内容完全不变时，仅改变示例在 Prompt 中的位置，也可能显著影响准确率和输出稳定性。

常见位置包括：

  • ssp：Start of System Prompt，系统提示词开头。
  • esp：End of System Prompt，系统提示词末尾。
  • sum：Start of User Message，用户消息开头。
  • eum：End of User Message，用户消息末尾。

经验上，示例放在开头，尤其是 system prompt 开头，通常更稳定；示例放在用户消息末尾，可能导致模型忽略或输出波动。小模型通常更容易受示例位置影响，大模型相对没那么敏感，但仍然需要实验验证。

这说明 Prompt 设计不只关心“写什么”，也要关心“放哪里”。

# 高阶 Prompt 优化方法

基础 Prompt 解决的是“怎么把任务说清楚”，高阶 Prompt 优化解决的是“怎么让模型更可靠地完成复杂任务”。

这类方法不只是改一句提示词，很多已经进入 Agent 工程范畴：通过多次调用、多路径推理、反思修订、工具调用和反馈循环，提高结果的稳定性和可执行性。

# Chain of Thought：思维链

Chain of Thought，简称 CoT，核心思想是引导模型不要直接给结论，而是先把问题拆开，一步一步分析，再得出答案。

最简单的写法是在 Prompt 里加入：

请一步一步分析后再回答。
1

CoT 适合复杂推理任务，例如：

  • 多步骤数学题。
  • 逻辑推理。
  • 业务规则判断。
  • 方案分析。
  • 多条件决策。
  • 工具调用前的任务拆解。

它的价值不只是提高最终答案准确率，更重要的是让模型先构建一条清晰的逻辑路径。只有模型知道“问题应该拆成哪几步”，后续才更容易判断哪一步需要查知识库、哪一步需要调用工具、哪一步需要后端代码计算。

但要注意：CoT 不能保证计算 100% 正确。LLM 本质上仍然不是计算器，它可能在推理过程的某一步算错。涉及金额、库存、利息、税费等场景时，应该让模型负责拆解和解释，让代码、数据库或工具负责精确计算。

工程建议：

  • 用户可见结果里不一定展示完整推理链，避免输出冗长或暴露不必要的中间过程。
  • 可以要求模型输出“简要推理依据 + 最终结论”，而不是展开所有内部推理。
  • 如果任务涉及工具调用，可以让模型先输出任务步骤，再由后端决定是否调用工具。

# Self-Consistency：自我一致性

Self-Consistency 是一种“少数服从多数”的稳定性增强方法。

它的做法是：对同一个问题进行多次推理，得到多个答案和推理路径，然后选择出现次数最多、最一致的结论作为最终答案。

基本流程：

  1. 使用同一个 Prompt 调用模型 3、5、7 次，最好是奇数次。
  2. 收集每次输出的推理路径和最终结论。
  3. 对结果进行汇总、统计或再交给模型判断一致性。
  4. 选择多数结论或置信度最高的结论输出。

它适合：

  • 复杂判断。
  • 多角度分析。
  • 非唯一但需要稳妥结论的问题。
  • 高价值离线任务。
  • Agent 任务中的结果校验。

优化建议：

  • 多次调用可以并发执行，降低整体耗时。
  • 可以适当提高 temperature 或使用不同模型，增加推理路径多样性。
  • 最终汇总时要保留每个答案的来源和理由，方便审计。

代价也很明显：调用次数更多，成本更高，延迟更大。所以它更适合高价值任务，不适合每个普通问答都使用。

# Tree of Thoughts：思维树

Tree of Thoughts，简称 ToT，核心思想是：不要满足于第一条推理路径，而是像下棋一样生成多种候选方案，分别评估，再选择最优解。

传统 CoT 更像“一条路走到底”，如果第一步方向错了，后面可能越推越偏。ToT 则要求模型先生成多个分支，再评估每个分支的优缺点。

典型流程：

  1. 分解任务。
  2. 生成多个候选思路或方案。
  3. 分别评估每个方案的优缺点、风险和适用场景。
  4. 综合比较，选择最优方案。

示例：

# 任务
设计订单到期自动关闭方案。

# 步骤
1. 设计 3 种可行方案。
2. 分别评估每种方案的优点、缺点、复杂度和风险。
3. 综合比较后，选择一个最适合生产环境的方案。
4. 给出最终推荐方案和原因。

  • 架构设计。
  • 技术选型。
  • 产品方案比较。
  • 风险评估。
  • 多策略决策。

工程上可以把 ToT 理解成“让模型先做方案集，再做评审和选择”。它比单次回答更全面，但同样会消耗更多 token 和时间。

# Reflection：反思机制

Reflection 是让模型自我批判、自我修正的策略。它通常不是单次调用，而是多轮调用：

  1. 先生成初步答案。
  2. 再让模型基于原始问题审查这个答案。
  3. 如果发现问题，输出修改建议。
  4. 再基于修改建议生成修订版。
  5. 最后输出最终答案。

可以理解为：一个模型先写，另一个模型或同一个模型再审，最后再改。

典型流程：

生成初稿 -> 反思审查 -> 修订答案 -> 再审查 -> 输出最终答案
1

Reflection 适合：

  • 长文档总结。
  • 方案设计。
  • 代码审查。
  • 高质量报告生成。
  • Agent 执行结果校验。

它的优势是可以显著提高答案质量，减少遗漏和明显错误。缺点是成本和延迟都会增加。如果循环次数太多，还可能导致上下文不断堆叠，出现上下文爆炸。

工程建议：

  • 设置最大反思轮次，避免无限循环。
  • 反思阶段只保留问题清单和修改建议，不要重复塞入全部冗长内容。
  • 对长内容先做摘要压缩，再进入下一轮审查。
  • 在线实时问答慎用多轮 Reflection，离线报告和高价值任务更适合。

# CoT、Self-Consistency、Reflection 的区别

这几个概念容易混，要分清它们不在同一层级：

方法 核心关注点 调用方式 适合场景
CoT 单次回答中先拆解推理步骤 通常一次调用 复杂推理、任务拆解
Self-Consistency 多次推理后取多数或一致结论 多次并行调用 高可靠判断、复杂决策
Reflection 生成后再审查和修订 多轮调用 报告、方案、代码审查
ToT 生成多条候选路径并评估选择 单次或多轮调用 方案比较、架构设计

CoT 更像“让模型想清楚”，Self-Consistency 更像“让多个答案投票”，Reflection 更像“写完后自查修改”，ToT 更像“先列多种方案再选优”。

# ReAct：推理加行动

ReAct 是 Reason and Act 的缩写，意思是把推理和行动结合起来。它是 Agent 的关键思想之一。

普通 Prompt 主要让模型回答问题；ReAct 则让模型在完成复杂任务时不断循环：

思考 -> 行动 -> 观察 -> 再思考 -> 再行动 -> 最终总结
1

每一轮大致做四件事：

  1. 思考：分析当前任务，决定下一步做什么。
  2. 行动：选择并调用工具，例如搜索、计算、查库、调用 API。
  3. 观察：读取工具返回结果。
  4. 总结或继续：判断任务是否完成，未完成则继续下一轮。

ReAct 的意义是让模型不再只是“生成文本”，而是可以和外部世界交互。比如：

  • 不知道最新信息时，调用搜索工具。
  • 需要精确计算时，调用计算器或代码执行工具。
  • 需要企业知识时，调用知识库检索。
  • 需要业务数据时，调用后端 API。

从 Java 后端视角看，ReAct 不是让模型随便执行动作，而是由后端暴露受控工具，并负责权限校验、参数校验、超时、重试、审计和幂等。

典型 Agent 架构中可以这样分工：

  • LLM：负责理解任务、规划步骤、选择工具。
  • Tool / MCP / Function Calling：负责执行外部动作。
  • Java 后端：负责工具注册、权限、参数校验、业务规则和审计。
  • Memory / RAG：负责提供历史信息和知识上下文。
  • Trace：负责记录每一步思考、行动和观察结果。

ReAct 适合复杂、多步骤、需要外部信息或外部动作的任务。但它也更容易带来成本、延迟、安全和不可控问题，因此必须设置最大步数、工具白名单、权限边界和失败策略。

# 提示词设计需要迭代

提示词设计很像“炼丹”：不是写出一版看起来完美的 Prompt，就一定能稳定生效。模型输出会受到很多因素影响：

  • 模型自身的指令遵循能力。
  • 模型参数规模和训练特性。
  • 任务复杂度。
  • 示例数量和示例质量。
  • 示例在 Prompt 中的位置。
  • 上下文窗口大小。
  • 历史会话和 RAG 资料占用。
  • temperature 等生成参数。

所以 Prompt Engineering 不是一次性写文案，而是一个持续实验、观察、评估和优化的过程。

每次调整 Prompt，都应该关注：

  • 任务是否完成。
  • 格式是否稳定。
  • 是否减少幻觉。
  • 是否符合业务规则。
  • 成本和上下文占用是否可接受。
  • 换模型后是否仍然稳定。

# 工程落地建议

# Prompt 要模板化

不要把 Prompt 散落在代码里。应该用模板管理 system prompt、user prompt、few-shot 示例、RAG 上下文和输出格式。

# Prompt 要版本化

每次修改 Prompt 都可能改变线上行为。建议记录版本、修改原因、适用模型和评测结果。

# Prompt 要可测试

准备一批标准问题和坏案例，每次改 Prompt 都跑一遍，观察准确率、格式稳定性、拒答率、幻觉率、成本和延迟。

# Prompt 要灵活组合

不要机械套模板。真实任务中可以把多个框架组合起来，例如用 ICIO 管理输入输出，用 TIDD-EC 增加禁止事项，用 Few-shot 稳定格式，用 CoT 或 ToT 做复杂推理。

# Prompt 不能替代后端校验

Prompt 可以约束模型，但不能作为安全边界。涉及金额、权限、订单、库存、删除、支付、发通知等动作，必须由 Java 后端做参数校验、权限校验、幂等控制和审计。

# 面试速记

# Prompt Engineering 是什么

Prompt Engineering 是通过设计角色、任务、上下文、约束、示例和输出格式，引导模型稳定完成任务的工程方法。它的目标是提升输出准确性、可控性和一致性。

# 如何写一个好 Prompt

一个好的 Prompt 通常包括角色、任务、上下文、约束、输出格式和必要示例。任务要具体，格式要明确，复杂场景要结构化，涉及程序处理时要规定 JSON Schema 或固定字段。

# 常见结构化 Prompt 框架有哪些

RTF 适合简单任务；ICIO 适合有上下文和明确输入输出的任务；CRISPE 适合策略分析和创意内容；CO-STAR 适合面向明确受众的复杂输出；TIDD-EC 适合规则强、禁区明确的任务；BROKE 适合目标导向和持续优化的方案类任务。

# Zero-shot 和 Few-shot 区别

Zero-shot 不给示例，适合简单通用任务；Few-shot 给少量输入输出示例，适合复杂分类、风格模仿、结构化抽取和工具路由，但会占用更多上下文。

# System Prompt 和 User Prompt 区别

System Prompt 是应用开发者设置的全局规则，用来约束角色、风格、安全边界和输出格式；User Prompt 是用户当前输入，决定本次任务内容。用户输入不可信，不能把安全边界完全交给 User Prompt。

# Prompt 的局限是什么

Prompt 能提升模型输出质量，但不能保证事实一定正确，也不能替代 RAG、工具调用、后端校验和评测。生产系统必须把 Prompt 和代码、知识库、工具、监控结合起来。

# CoT、ToT、Reflection、ReAct 怎么区分

CoT 是单次调用中引导模型分步推理；ToT 是生成多条候选思路并评估选择；Reflection 是生成答案后再审查和修订；ReAct 是让模型在推理过程中调用工具、观察结果并继续规划。它们从 Prompt 技巧逐渐走向 Agent 工程。
