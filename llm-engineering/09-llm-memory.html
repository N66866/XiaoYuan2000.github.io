# LLM 记忆

# 本章导读

标准 LLM 请求是无状态的。模型不会因为上次和用户聊过，就在下一次请求中自动记得用户；应用必须保存信息，并在需要时重新注入 Context。

真正的长期记忆不是无限保存聊天记录，而是对跨会话有价值的信息进行提炼、身份隔离、按需检索和生命周期管理。

原始交互
-> 提取候选记忆
-> 判断新增、更新、删除或忽略
-> 持久化并建立索引
-> 新任务按需召回
-> 注入当前 Context

# 1. 短期记忆、持久化记忆与长期记忆

# 1.1 短期记忆

短期记忆服务于当前会话或任务，常见内容包括：

  • 最近几轮 User、Assistant 和 Tool 消息。
  • 当前计划、节点状态和工具结果。
  • 临时变量、失败信息和待办事项。

它通常直接进入模型上下文，受 Token 窗口限制。会话结束、任务完成或达到清理条件后可以丢弃或归档。

# 1.2 持久化不等于长期记忆

JdbcChatMemoryRepository 等组件可以把会话消息保存到 MySQL、Redis 或 Cassandra，使服务重启后继续同一 conversationId。这解决的是分布式部署和会话恢复，本质上仍可能是持久化的短期记忆。

长期记忆至少还应具备：

  • 跨会话和跨任务复用。
  • 从交互中提炼稳定事实、偏好或经验。
  • 按用户、租户、Agent 等身份隔离。
  • 根据当前任务检索相关记忆，而不是重放全部历史。
  • 处理冲突、更新、过期、遗忘和用户删除。

因此：长期记忆一定需要持久化，但持久化的数据不一定是长期记忆。

# 1.3 记忆进入 Context 才会生效

模型不会直接读取数据库。记忆必须经过检索、过滤、格式化后注入当前请求：

数据库中的记忆 != 模型当前记得
检索并注入 Context 的记忆 = 模型本轮可使用的信息
1
2

这也是 Memory 与 Context 的边界：Memory 负责窗口之外的保存与检索，Context 是本次调用实际可见的 Token。

# 2. 记忆类型

类型 保存内容 示例
Working Memory 当前步骤正在处理的信息 当前报错、正在修改的文件
Session Memory 当前会话或任务历史 最近消息、工具结果、任务进度
Semantic Memory 抽取后的稳定事实 用户是 Java 开发者、偏好清淡口味
Episodic Memory 过去发生的事件和结果 元旦去了三亚、上次部署失败原因
Procedural Memory 可复用规则、技能和经验 发布前必须运行哪些检查
Profile Memory 结构化用户画像 常住地、语言、通知偏好

这些分类可以重叠。例如“用户喜欢清淡口味”既可作为 Semantic Memory 存入向量库，也可作为 Profile Memory 的结构化字段。

任务状态不一定都适合长期保留。Checkpoint 主要服务流程恢复，只有经过验证、未来可复用的经验才应提炼为长期记忆。

# 3. 什么值得记住

# 3.1 建议保存

  • 用户明确表达且相对稳定的偏好。
  • 经用户确认的身份、目标和项目背景。
  • 可复用的业务规则、团队规范和操作经验。
  • 具有长期价值的任务结论与失败模式。
  • 未来请求明确可能依赖的重要事件。

# 3.2 不应直接保存

  • 寒暄、重复表达和无后续价值的内容。
  • 一次性搜索结果、临时工具输出和完整错误堆栈。
  • 模型未经验证的推测或幻觉。
  • 密码、密钥、支付信息等高敏感数据。
  • 没有用户授权或业务合法依据的个人信息。
  • 已经过期、被用户纠正或要求删除的内容。

工具结果不能一概忽略。稳定的故障解决经验可以在验证后提炼为 Procedural Memory，但不应把整段日志永久保存为用户画像。

# 3.3 记忆粒度

记忆条目应保持原子化，便于更新和检索：

不推荐：用户喜欢 Java、住在杭州、最近准备面试，而且不吃香菜。
推荐：
- 职业方向：Java 开发
- 当前目标：准备技术面试
- 饮食偏好：不吃香菜
- 常住地：杭州

# 4. 长期记忆生命周期

# 4.1 提取候选记忆

在交互结束后，由规则或 LLM 从 User/Assistant 消息中抽取候选事实。提取 Prompt 应要求：

  • 只记录用户明确表达或已验证的事实。
  • 区分长期状态、临时事件和推测。
  • 输出结构化字段和证据来源。
  • 对不值得记录的对话返回空集合。

Assistant 自己生成的内容不能自动成为用户事实。例如模型建议用户去上海，不代表“用户住在上海”。

# 4.2 与已有记忆比较

新候选应与相同主体、类型或语义相近的旧记忆比较，再执行：

操作 使用场景
ADD 新事实，不与已有记忆重复或冲突
UPDATE 同一事实发生变化或得到更准确信息
DELETE 用户否认、要求删除或数据不再允许保存
NOOP 重复、低价值、证据不足或无需变化

# 4.3 处理冲突和时间语义

用户先说“我住在北京”，后来又说“我搬到上海了”，可以更新当前居住地，并将旧值标记为 superseded 或保留有效期历史。

但“我这周在上海出差”不能覆盖常住地。系统需要判断：

  • 这是长期状态变化还是临时事件。
  • 新旧信息的发生时间和有效时间。
  • 来源是否为用户本人或权威系统。
  • 是否需要澄清，而不是盲目覆盖。

推荐将结构化事实设计为：

subject + attribute + value + validFrom + validTo + source + confidence
1

# 4.4 检索与注入

新请求到来时，根据当前问题检索记忆，并综合：

  • 语义相关性。
  • 用户、租户、Agent 与任务范围。
  • 时间衰减和有效期。
  • 重要性与用户确认状态。
  • 来源可信度和 Token 预算。

召回结果应放入独立的 LONG_TERM_MEMORY 区域，明确它是辅助背景而不是高优先级系统指令。模型回答时仍要以当前用户意图和权威业务数据为准。

# 4.5 遗忘与删除

长期记忆不能无限增长。常见策略包括：

  • TTL：临时兴趣、短期目标到期自动失效。
  • 衰减：长期未使用且重要性低的记忆降低召回权重。
  • 合并：将重复事件压缩为一条总结。
  • 归档：从在线索引移出，但保留合规要求的历史。
  • 删除：用户请求后从主存储、索引和缓存中清除。

删除需要考虑向量库、关系库、图数据库、缓存和备份等多份副本，不能只删一个索引条目。

# 5. 存储架构

# 5.1 向量数据库

适合对偏好、经历、总结和经验做模糊语义检索。缺点是精确过滤、唯一性和事务能力通常不如关系数据库。

# 5.2 关系型数据库

适合用户等级、购买时间、当前住址、任务状态等结构化事实，可以精确查询、建立唯一约束并进行事务更新。

# 5.3 图数据库

适合实体关系和多跳遍历，例如“张三是李四的同事，李四负责 A 项目”。图数据库便于关系查询，但不会自动保证实体抽取和关系推理正确。

# 5.4 文件与规则

用户显式配置、团队规范和项目约束可保存在 AGENTS.md、规则文件或 Skill 中。这类 Procedural Memory 版本清晰、可审核，通常比从对话中隐式猜测更可靠。

# 5.5 混合架构

生产系统常将多种存储组合：

flowchart LR
    A["对话与任务"] --> E["记忆提取和合并"]
    E --> S["关系库：身份、事实、版本"]
    E --> V["向量库：语义记忆"]
    E --> G["图数据库：实体关系"]
    E --> O["对象存储：原始证据"]
    Q["当前问题"] --> R["身份过滤和多路检索"]
    S --> R
    V --> R
    G --> R
    O --> R
    R --> C["注入 Context"]

关系库通常承担记忆主键、所有权、版本和生命周期；向量库负责语义召回；对象存储保存可追溯证据。

微调不适合作为普通用户记忆的主要实现。它更新慢、难以精确删除和追溯，也不适合每个用户频繁变化的事实。微调更适合改变任务能力、风格和输出分布。

# 6. 身份、权限与隐私

# 6.1 记忆作用域

常见标识包括：

标识 含义
tenantId 企业或租户隔离边界
userId 用户长期画像与偏好
agentId 特定 Agent 的经验或配置
runId / threadId 单次任务或会话状态

userId 只是检索分区条件，不等于身份认证。服务端必须从可信登录态获得用户和租户，不能直接相信请求参数中的 userId。

# 6.2 安全要求

  • 写入前取得合法依据和必要授权。
  • 只保存完成业务目的所需的最少信息。
  • 传输和存储加密，对敏感字段单独保护。
  • 检索前执行租户、用户和数据权限过滤。
  • 提供查看、纠正、导出和删除入口。
  • 记录谁在何时写入、读取、修改或删除了记忆。

错误记忆会长期污染后续回答，因此应保留来源和证据，低置信度内容不得静默升级为用户事实。

# 7. Mem0 的架构与原理

Mem0 是长期记忆编排框架，不是单纯的数据库。它协调：

  • LLM：提取候选记忆、判断冲突和生成更新操作。
  • Embedding Model：将记忆和查询向量化。
  • Vector Store：进行语义召回。
  • Graph Store：可选，用于保存实体关系。
  • History/Metadata Store：保存记忆版本和操作历史。

# 7.3 REST API

Mem0 REST Server 可将 Python 记忆能力通过 HTTP 暴露给 Java 应用。常见能力包括：

  • 添加记忆。
  • 根据 userId 和查询检索记忆。
  • 获取、更新或删除指定记忆。
  • 查看历史或清理用户记忆。

具体端点和初始化方式随版本变化，应以部署版本的 OpenAPI 文档为准。生产环境还需要鉴权、TLS、超时、限流和审计，不能把记忆服务裸露在网络中。

# 8. Spring AI Alibaba 接入 Mem0

# 8.1 核心类

类 / 常量 作用
Mem0ChatMemoryAdvisor 在 ChatClient 调用前检索并注入记忆，调用后触发写回
Mem0ServiceClient 封装对 Mem0 REST Server 的 HTTP 调用
Mem0MemoryStore / VectorStore 向 Advisor 暴露记忆查询与写入能力

        .defaultAdvisors(memoryAdvisor)
        .build();

        .advisors(advisor -> advisor.params(Map.of(USER_ID, trustedUserId)))
        .call()
        .content();

# 8.2 调用前后发生什么

调用前：Advisor 使用当前问题和用户范围查询 Mem0，将相关记忆格式化后加入 Context。

调用后：Advisor 将本轮交互交给 Mem0，Mem0 提取候选记忆并执行新增、更新、删除或忽略。不是把整段对话无条件写成长期记忆。

# 8.3 服务不可用时

记忆通常是增强能力，不应无条件阻塞整个 Spring Boot 应用启动。可采用：

  • 用配置开关和条件 Bean 控制是否启用 Mem0。
  • 延迟初始化客户端，并配置较短的连接与请求超时。
  • 使用健康检查、熔断和隔离，防止记忆服务拖垮聊天接口。
  • 检索失败时降级为无长期记忆对话，并记录可观测事件。
  • 写入失败时进入受控重试或事件队列，避免丢失且不阻塞主响应。

简单使用 @Lazy 可以推迟连接，但不能代替健康检查、超时、熔断和失败降级。

# 9. 评测与质量治理

长期记忆至少评估：

  • Extraction Precision：保存的内容是否真的值得记。
  • Retrieval Recall/Precision：需要的记忆能否召回，是否混入无关记忆。
  • Conflict Resolution：新旧事实能否正确更新。
  • Attribution：记忆能否追溯到用户原话或权威来源。
  • Personalization Gain：记忆是否实际改善回答，而非生硬插入。
  • Privacy Leakage：是否发生跨用户、跨租户召回。
  • Forgetting Compliance：删除或过期后是否还会被召回。

应构造包含重复事实、临时事件、矛盾信息、敏感数据和跨用户攻击的评测集，而不只测试“我喜欢什么”这一类理想案例。

# 10. 常见误区

# 误区一：把所有历史消息存入 MySQL 就是长期记忆

这通常只是可恢复的会话历史。长期记忆还需要提炼、跨会话检索和生命周期管理。

# 误区二：所有对话都值得记住

无差别写入会造成隐私风险、记忆污染、存储膨胀和召回噪声。

# 误区三：向量相似就代表事实正确

向量相似度只表示语义接近，不表示来源可信、当前有效或属于当前用户。

# 误区四：新记忆和旧记忆冲突时直接覆盖

必须理解时间语义、来源和事实类型；必要时保留历史或向用户澄清。

# 误区五：userId 已经解决权限问题

userId 只是数据分区键，身份认证和授权必须由服务端独立完成。

# 11. 面试速答

# 11.1 长期记忆与持久化聊天记录有什么区别？

持久化聊天记录主要用于恢复同一会话；长期记忆会从交互中提炼跨会话有价值的事实和经验，按用户隔离、按需检索，并支持冲突更新、过期和删除。

# 11.2 长期记忆的完整流程是什么？

从交互中提取候选记忆，与已有记忆比较后执行新增、更新、删除或忽略，再持久化和建立索引。新任务到来时按身份、相关性、时效和权限召回，最后注入当前 Context。

# 11.3 向量库、关系库和图数据库如何分工？

向量库负责偏好和经历的语义召回，关系库负责身份、结构化事实、版本和事务，图数据库负责实体关系遍历；生产系统通常采用混合存储。

# 11.4 Mem0 是什么？

Mem0 是由 LLM 驱动的长期记忆编排层，协调记忆提取、冲突处理、Embedding、向量检索、可选图关系和历史存储，并通过 add 与 search 管理记忆生命周期。

# 11.5 如何防止长期记忆污染和越权？

只保存用户明确或已验证的信息，记录来源和有效期，写入前去重与冲突检测；检索时按租户和用户做服务端权限过滤，并提供查看、纠正、删除和审计能力。
