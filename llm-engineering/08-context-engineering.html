# Context Engineering 上下文工程

# 本章导读

Context Engineering 关注如何在有限上下文窗口中，让模型看到完成当前任务所需的最小充分信息。

Prompt Engineering 主要优化“怎样向模型表达任务”，Context Engineering 则决定“这一轮到底让模型看到什么”。后者管理的不只是 Prompt，还包括历史消息、记忆、RAG 资料、工具定义与结果、任务状态和安全规则。

Prompt Engineering：把话说清楚
Context Engineering：把正确的信息在正确的时机交给模型
1
2

上下文不是越长越好。目标是在相关性、真实性、完整性、Token、延迟和成本之间取得平衡。

# 1. Token、Prompt、Context 与 Memory

概念 定义 工程关注点
Token 模型编码和处理文本的单位 上下文窗口、输入输出计费、截断
Prompt 本轮任务的指令、问题、示例和格式约束 清晰、具体、无冲突、可复用
Context 模型本次推理实际看到的全部 Token 选择、排序、压缩、隔离、预算
Memory 应用保存并按需取回信息的机制 提炼、存储、检索、更新、遗忘

Token 不是固定数量的汉字或英文单词，其切分取决于模型的 Tokenizer。字符数只能粗略估算，生产系统应使用目标模型对应的 Tokenizer 或 SDK 计算。

Prompt 是 Context 的一部分。它不只是 User Message，还可能包含 System 指令、Few-shot 示例、任务模板和输出 Schema。

Context 通常包含四类内容：

  • Instructions：系统规则、用户任务、输出要求。
  • Knowledge：RAG 证据、长期记忆、业务资料。
  • Tools：工具 Schema、使用说明、Tool Call 与 Tool Result。
  • State：计划、任务进度、错误、审批结果等运行状态。

数据库、文件和向量库中的数据并不会自动成为 Context。只有应用将其选出、格式化并注入本次模型请求后，模型才能看到。

标准 LLM 调用本身是无状态的。所谓短期记忆和长期记忆都由应用层维护，并在需要时重新注入 Context。更完整的记忆设计见 LLM 记忆。

# 2. 为什么长上下文不一定更好

# 2.1 硬性成本

  • 超过模型上下文窗口会被截断或直接报错。
  • 输入 Token 增加推理成本和首 Token 延迟。
  • Agent 每轮都携带历史时，成本会随循环快速增长。
  • 大量工具结果和网页正文会挤压模型输出预算。

# 2.2 Lost in the Middle

长上下文模型对信息位置存在敏感性：关键证据位于开头或结尾时往往更容易被利用，埋在中间时可能被忽略。模型声明支持 128K 或更长窗口，不代表能够无损利用其中每一条信息。

因此应将核心任务、关键约束和最相关证据放在显著位置，并通过结构化标题、引用编号和末尾任务重述保持注意力。

# 2.3 四类上下文故障

问题 含义 示例
Context Poisoning 错误事实进入上下文并被持续沿用 一次幻觉被写入记忆，后续都以它为前提
Context Distraction 无关信息过多，稀释当前目标 长日志掩盖真正的报错行
Context Confusion 工具、选项或资料过多，导致选择错误 暴露几十个相似工具后调用了错误接口
Context Clash 同一上下文中存在互相矛盾的信息 新旧地址、规则版本或状态同时生效

这些问题可能同时出现。治理重点是记录来源、版本、时间和可信度，并在进入模型前去重、过滤和处理冲突。

# 3. 四种核心策略

上下文工程可以归纳为 Write、Select、Compress、Isolate。

# 3.1 Write：写到窗口之外

将未来可能需要、但当前不必一直携带的信息写入外部存储：

  • Scratchpad：计划、待办、临时结论和失败记录。
  • Checkpoint：工作流或 Agent 的完整执行状态。
  • 长期记忆：跨会话有价值的用户事实与经验。
  • 文件/对象存储：网页、PDF、日志和大型工具结果。

Write 不是保存所有内容。应保存原始数据引用、关键事实、来源、时间和可重建信息，并设置生命周期。

# 3.2 Select：只取当前相关内容

根据当前目标动态选择：

  • 语义相关且属于当前用户的长期记忆。
  • 通过权限过滤的 RAG 片段。
  • 当前任务需要的规则文件和代码文件。
  • 最匹配的工具或工具组。
  • 未完成计划、最近错误和当前工作状态。

选择策略不仅看向量相似度，还要结合权限、时效、可信度、任务阶段和 Token 预算。任何越权过滤都应由后端代码完成，不能交给模型自行决定。

# 3.3 Compress：降低 Token 占用

常见方式包括：

  • Summarization：把长对话和执行轨迹压缩为结构化摘要。
  • Trimming：按规则移除过旧消息或冗长工具输出。
  • Pruning：识别并删除与当前任务无关的内容。
  • Extractive Compression：保留原文中的关键句、字段和引用。

摘要是有损压缩，不能替代源数据。重要数字、错误码、文件路径、未完成项和决策依据应结构化保留，同时保留源文件引用，便于重新读取。

# 3.4 Isolate：拆分并隔离

  • 子 Agent 使用独立上下文专注子任务，只向主 Agent 返回结论和证据。
  • 代码和浏览器操作放入沙箱，仅回传必要结果。
  • 大文件保存在外部存储，Context 只保留路径和摘要。
  • State 区分内部字段和暴露给 LLM 的字段。
  • 不同租户、用户和安全域使用独立检索范围。

隔离既减少上下文干扰，也降低工具执行和不可信内容造成的安全风险。

# 3.5 Progressive Disclosure：渐进式披露

先给模型能力目录和简短说明，确认需要后再加载完整 Skill、工具说明、规则或文档。例如先提供“数据库规范位于 docs/db.md”，只有执行数据库任务时才读取全文。

它能降低初始上下文体积和工具混乱，但目录描述必须足够清楚，否则模型不知道何时继续加载。

# 4. 上下文组装流程

生产系统不应在 Controller 中随手拼字符串，而应构建独立的 Context Builder：

    Q["当前任务"] --> I["意图与任务阶段"]
    I --> S["选择记忆、知识、工具和状态"]
    S --> P["权限、来源和冲突校验"]
    P --> B["Token 预算与压缩"]
    B --> O["排序和结构化组装"]
    O --> M["模型调用"]

推荐的组装顺序是：

  1. 固定且版本化的系统规则。
  2. 当前用户目标和不可违反的约束。
  3. 当前计划、进度与最近一次失败摘要。
  4. 经过权限过滤的记忆和外部证据。
  5. 当前可用工具定义。
  6. 必要的近期消息与工具结果。
  7. 在尾部再次明确当前问题和输出格式。

具体顺序要通过评测验证，不存在适用于所有模型的固定模板。

输入预算再分配给系统指令、当前问题、状态、历史、RAG、记忆和工具定义。预算不足时，应优先移除低相关、低可信、过期和可重新获取的内容，而不是截断关键约束。

# 4.2 来源与冲突

每段动态上下文建议携带来源、时间、版本、权限和引用 ID。发生冲突时可以按以下顺序处理：

  1. 代码定义的安全规则高于外部资料。
  2. 权威业务系统高于模型生成摘要。
  3. 新版本通常高于旧版本，但要考虑有效期。
  4. 无法判断时保留冲突并向用户澄清，不能让模型猜。

# 5. KV Cache 与稳定前缀

Transformer 自回归生成时会缓存历史 Token 的 Key/Value，避免每生成一个 Token 都重新计算完整前缀。许多模型服务还支持跨请求的 Prompt/Prefix Cache，用于复用相同输入前缀。

如果 System Prompt、工具顺序、JSON 字段顺序或前缀中的动态时间不断变化，Token 序列也会变化，缓存命中率就会下降。

提高稳定性的做法：

  • System Prompt 模板版本化，避免无意义改动。
  • 不在固定前缀中插入每轮变化的时间戳或随机值。
  • 工具和结构化数据采用稳定排序与稳定序列化。
  • Agent 历史尽量追加，不回写修改已经发送的前缀。
  • 支持会话亲和的推理服务可将同一会话路由到可复用缓存的节点。

缓存能力和规则依赖具体模型供应商与推理框架，不能假设跨请求 KV Cache 一定存在。

# 6. 工具选择与缓存的权衡

上下文工程通常建议只暴露相关工具；Manus 的实践则强调保持工具定义稳定，以提高 Prefix Cache 命中率。两者解决的问题不同：

  • 动态裁剪工具：减少 Token 和选错工具，代价是前缀变化、缓存失效。
  • 稳定工具集：利于缓存复用，工具过多时可能干扰选择。

可采用折中方案：

  • 先由 Tool Router 选择领域，再加载该领域的固定小工具集。
  • 每个专业子 Agent 持有稳定、有限的工具集合。
  • 为工具使用统一前缀，例如 browser_*、file_*、db_*。
  • 在供应商支持时，使用受约束解码、工具白名单或响应预填充限制本轮工具。

是否保留全部工具要通过任务成功率、Token、延迟和缓存收益共同评估。

# 7. Manus 上下文实践

# 7.1 文件系统作为外部上下文

网页、PDF 和长日志不直接塞进模型窗口，而是写入沙箱文件：

完整内容：/workspace/research/page-17.html
Context：已保存页面 17；来源 URL=...；摘要=...；需要时按段读取
1
2

这比只保留不可恢复的摘要更可靠。路径、来源、内容哈希和范围让 Agent 能重新获取原文。

# 7.2 用待办清单保持目标显著

长任务中动态维护 todo.md，每一步更新完成项、当前项、下一步和阻塞原因，并在上下文末尾注入精简版本，可以缓解对初始目标的遗忘。

任务清单应是结构化状态的投影，而不是另一个可能与真实状态冲突的事实源。

# 7.3 保留可操作的失败信息

Agent 需要看到错误才能换策略，但不应无限追加完整堆栈。建议：

  • 完整日志外存，Context 保留错误摘要和文件引用。
  • 记录已尝试方案、失败原因和不可重复动作。
  • 连续出现相同错误时触发循环检测、降级或人工介入。

失败信息的价值在于帮助下一轮决策，而不是让上下文成为日志仓库。

# 8. 安全与可观测性

# 8.1 Prompt Injection 隔离

网页、邮件、RAG 文档和工具结果都是不可信数据。应明确使用结构化边界将“系统指令”和“待分析内容”分开，并在工具执行前再次进行权限、参数和业务校验。

不能仅靠一句“忽略文档中的指令”防御 Prompt Injection。还要限制工具权限、过滤敏感数据、隔离执行环境和审计高风险动作。

# 8.2 上下文 Trace

每次模型调用应能回答：

  • 哪些信息被选入，为什么被选入。
  • 哪些内容因预算被压缩或移除。
  • 来源、版本、权限和相关性分别是什么。
  • 使用了多少输入 Token，缓存是否命中。
  • 哪段上下文可能导致错误决策。

动态上下文必须可解释、可回放，才能将坏案例转化为评测集和回归测试。

# 9. 常见误区

# 误区一：上下文等于聊天历史

聊天历史只是 Context 的一部分。Context 还包含系统指令、工具、知识、记忆和状态。

# 误区二：模型窗口越大，效果一定越好

更大的窗口只提高容量，不保证所有信息都被正确利用。无关、错误和冲突内容还会降低质量。

# 误区三：数据已经存入数据库，模型就记住了

存储解决“信息没有丢”，选择与注入才解决“模型本轮能看到”。

# 误区四：摘要后可以删除原始数据

摘要可能漏掉数字、限定条件和证据。重要内容应保留原文或可恢复引用。

# 误区五：把所有工具都给 Agent 最灵活

工具过多会增加 Token 和选择错误。应按领域分组、动态选择或隔离到专业子 Agent，并评估缓存权衡。

# 10. 面试速答

# 10.1 Prompt Engineering 与 Context Engineering 有什么区别？

Prompt Engineering 优化单次任务的表达方式；Context Engineering 管理模型本轮能看到的全部信息，包括指令、历史、记忆、RAG、工具和状态，核心是选择、压缩、隔离与预算。

# 10.2 Context Engineering 的四种核心方法是什么？

Write 将重要信息写到窗口外，Select 按任务召回相关信息，Compress 对长内容摘要或裁剪，Isolate 用子 Agent、沙箱、文件和结构化 State 隔离不同上下文。

# 10.3 为什么上下文不是越多越好？

长上下文会增加 Token、延迟和成本，还可能产生中间信息丢失、错误污染、注意力分散、工具混乱和信息冲突。目标不是塞满窗口，而是提供最小充分上下文。

# 10.4 如何管理 Agent 的大型工具结果？

将完整结果保存到文件或对象存储，在 Context 中只放结构化摘要、来源和可恢复引用；需要细节时按范围读取，同时保留最近错误和当前任务进度。

# 10.5 动态工具裁剪为什么可能影响缓存？

工具定义通常位于输入前缀，动态增删或改变顺序会改变 Token 序列，降低 Prefix Cache 命中率。可用领域路由、固定小工具集和专业子 Agent 在选择准确率与缓存收益之间平衡。
