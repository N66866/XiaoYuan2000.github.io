# Harness 与 Loop Engineering

# 本章导读

模型能力强，不代表 Agent 能稳定完成任务。只调整 Prompt 和 Context，仍无法解决工具越权、执行失败、循环失控、环境污染、结果未验证和任务中断等运行时问题。

Harness Engineering 关注如何在 LLM 外部建立一套执行环境，用编排、工具、状态、验证、安全、恢复和可观测性约束模型能力，使 Agent 能持续、稳定、可评估地工作。

Loop Engineering 则把视角扩展到一个自治任务从触发到交付的完整生命周期：谁触发、在哪里运行、如何验证、何时重试、怎样停止、失败后如何恢复、产物交给谁。

这些术语仍在演化，边界并非正式标准。真正重要的是它们所强调的工程机制，而不是概念命名。

# 1. Prompt、Context 与 Harness

层级 核心问题 典型手段
Prompt Engineering 怎样清楚描述单次任务 角色、任务、约束、示例、输出格式
Context Engineering 本轮让模型看到什么 选择、检索、压缩、隔离、Token 预算
Harness Engineering 模型能力如何安全、稳定地运行 编排、工具、状态、验证、权限、恢复、观测

Harness 通常包含 Prompt 和 Context 管理，但增量不在于“再写一种提示词”，而在于把模型放进一个受控运行时：

输入与上下文准备
-> 模型决策
-> 权限和参数校验
-> 执行动作
-> 外部验证
-> 反馈、修复或终止
-> 保存状态、指标和产物

常见概括是：

Agent = LLM + Harness

它强调 LLM 只是推理核心，真正可交付的 Agent 还需要模型之外的执行系统。

# 2. 为什么需要 Harness

LLM 的输出具有概率性，Agent 又会将输出转换为真实动作。风险包括：

  • 模型声称完成任务，实际代码不能编译或页面不可用。
  • 工具参数错误、重复调用或越权访问生产数据。
  • 长任务中目标漂移，反复尝试相同失败方案。
  • 服务重启后状态丢失，只能从头开始。
  • 多个 Agent 修改同一工作区，互相覆盖文件。
  • 结果无法回放，不知道哪条指令、工具或上下文导致失败。
  • 模型升级或 Prompt 修改后质量悄悄退化。

Harness 将这些失败模式转化为可编程组件和硬约束，让质量不只依赖模型“自觉”。

# 3. Harness 的六个核心部分

# 3.1 上下文管理

动态加载当前任务需要的规则、代码、知识和记忆，并在超过预算时摘要、裁剪或外存。常见方式包括：

  • 根据任务阶段加载对应文档和工具组。
  • 使用 AGENTS.md 或能力目录做渐进式披露。
  • 将网页、日志和大型产物写入文件，只回传引用和摘要。
  • 对历史消息和工具结果做压缩。

Context Engineering 是 Harness 的重要子系统，详见 Context Engineering。

# 3.2 工具系统

不能只把工具定义交给模型，还要规定如何发现、选择、校验和执行：

  • 使用 Function Calling、MCP、API 或 CLI 连接外部能力。
  • 工具名、描述、参数和返回值清晰且结构化。
  • 按身份和任务授予最小权限。
  • 写操作执行鉴权、幂等、审计和必要的人审。
  • 对超时、限流、部分成功和副作用定义错误语义。
  • 将多步骤 SOP 封装为 Skill，减少模型临场拼装。

LLM 只提出 Tool Call，真正的工具执行者始终是 Agent Runtime。

# 3.3 状态与记忆

Harness 需要区分：

  • Working State：当前步骤、输入、错误和中间产物。
  • Session/Task State：计划、完成项、工具轨迹和检查点。
  • Long-term Memory：跨任务可复用的事实、偏好和经验。

持久化 Checkpoint 支持断点恢复，但恢复后的节点必须幂等。长期记忆还需要提炼、检索和生命周期管理，详见 LLM 记忆。

# 3.4 执行编排

大任务应拆成可验证的小步骤，并明确依赖关系、并行边界和人工 Gate：

理解目标 -> 制定计划 -> 执行最小步骤 -> 验证 -> 更新计划 -> 交付
1

编排器负责：

  • 选择串行、并行、路由或评估优化模式。
  • 将专业任务分派给不同 Agent 或模型。
  • 根据中间结果重规划，而不是机械执行旧计划。
  • 管理超时、预算、取消和最终状态。

确定性流程应由代码主控，LLM 处理模糊理解和开放决策。

# 3.5 评估与观测

Harness 不允许模型既当执行者又当唯一裁判。完成标准应尽量外置：

  • 代码任务：编译、测试、Lint、类型检查、安全扫描。
  • UI 任务：浏览器操作、截图、可访问性检查和视觉对比。
  • 数据任务：Schema、行数、约束、统计值和抽样验证。
  • RAG：检索评测、引用、忠实度和拒答测试。
  • Agent：任务完成率、工具正确率、步数、成本和人工接管率。

Trace 应记录模型、Prompt、Context、工具调用、状态迁移、耗时、Token、费用、验证结果和最终产物，支持回放与坏案例分析。

# 3.6 约束、校验与恢复

  • 架构约束：例如 UI 层不能直接访问数据库。
  • 权限约束：禁止访问无关目录、网络和生产凭证。
  • 输出校验：JSON Schema、枚举、类型和业务规则。
  • 循环约束：最大轮次、超时、预算和重复状态检测。
  • 环境隔离：Worktree、容器、沙箱和最小网络权限。
  • 故障恢复：限次重试、退避、降级、Checkpoint 和人工升级。

自愈不是无限重试。系统应将可操作的错误反馈给 Agent，并在重复失败或触达风险边界时停止。

# 4. 外部验证闭环

# 4.1 为什么不能相信“我检查过了”

模型自我评估容易延续生成时的错误假设，可称为自我评估偏差或相关性错误。让同一个模型再读一次答案，不能证明结果真实可用。

验证优先级通常是：

  1. 确定性程序校验和业务断言。
  2. 自动化测试、编译和真实环境操作。
  3. 独立数据源、模拟器或专用评测器。
  4. LLM Reviewer / LLM-as-Judge。
  5. 高风险场景的人工审核。

另一个模型可以提供不同视角，但仍可能犯相同错误，不能替代可执行验证。

反馈给 Agent 的内容应包含：

  • 失败的验证项和退出码。
  • 最相关的错误日志，而非无限完整输出。
  • 已尝试方案和禁止重复的动作。
  • 剩余预算、轮次和当前任务目标。

每次修复后先运行针对性验证，再运行受影响范围的回归测试，避免“修好一个、破坏另一个”。

# 5. AI Coding 中的 Harness

# 5.1 Prompt 层

用户提出“实现积分系统，并保持现有 API 兼容”。单独依赖 Prompt，模型可能生成看似合理但不符合项目架构的代码。

# 5.2 Context 层

运行时加载相关实体、服务、接口、数据库迁移规范、测试约定和 AGENTS.md，让模型理解项目语境。

# 5.3 Harness 层

Harness 进一步负责：

  1. 创建隔离 Worktree 或容器。
  2. 读取项目规则并制定计划。
  3. 限定可修改目录和可用工具。
  4. 修改代码并记录 Diff。
  5. 自动执行格式化、编译、测试和安全检查。
  6. 将失败诊断反馈给 Agent，限次修复。
  7. 检查修改范围和敏感文件。
  8. 验证通过后提交分支并创建 Draft PR。
  9. 由人类决定是否合并或发布。

这使交付物从“代码片段”变为“经过验证、可审查的变更”。

# 6. Harness 评测系统

Harness 不仅控制在线执行，也要建立离线评测和持续回归。

# 6.1 四个基础组件

组件 作用
Dataset 保存输入、参考资料、期望行为、标签和风险样例
Runner 批量执行并固定模型、Prompt、检索和工具版本
Judge 使用规则、程序、人工或 LLM 评分
Report 对比质量、成本、延迟和失败样例

# 6.2 评测对象

对象 关键指标
Prompt 指令遵循、格式通过率、拒答和稳定性
RAG 召回率、排序、引用、忠实度和完整性
Function Calling 工具选择、参数正确率、权限和失败恢复
Agent 任务完成率、步数、循环、成本、接管率
Workflow 节点成功率、恢复率、重复副作用和总耗时
Memory 提取准确率、召回、冲突更新和越权泄漏

# 6.3 LLM-as-Judge 的边界

LLM Judge 适合评价语气、覆盖度和开放式文本质量，但应：

  • 给出清晰 Rubric，并要求结构化评分和证据。
  • 隐藏候选版本名称，降低位置和品牌偏差。
  • 与人工标注样本校准一致性。
  • 对关键事实使用程序或权威数据验证。
  • 保存 Judge 模型和 Prompt 版本。

不能因为 Judge 给高分，就跳过编译、权限或业务规则校验。

# 6.4 回归闭环

线上失败、人工接管和用户纠正应脱敏后进入坏案例库：

线上 Trace
-> 归因失败类型
-> 添加回归样例
-> 修改 Prompt / Context / Harness
-> 批量评测
-> 达到质量与成本阈值后发布

# 7. Agent Loop 与 Loop Engineering

# 7.1 Agent Loop

Agent Loop 是单次任务内部的推理行动循环：

Reason / Decide -> Action -> Observation -> 下一轮决策
1

在代码中常表现为有限 while 循环，直到模型返回最终答案、任务完成或达到 maxIterations。

# 7.2 Loop Engineering

Loop Engineering 是覆盖 Agent Loop 外部的生产生命周期：

flowchart LR
    T["事件触发"] --> P["计划"]
    P --> E["隔离执行"]
    E --> V["外部验证"]
    V -->|"失败"| F["反馈与重规划"]
    F --> E
    V -->|"通过"| O["提交产物"]
    V -->|"需要决策"| H["人工介入"]

关键差别：

维度 Agent Loop Loop Engineering
范围 单个任务内部 跨步骤、会话、Agent 和系统
触发 用户或程序调用 Cron、Webhook、CI、Issue、事件流
验证 Agent 自己判断或简单检查 强制外部测试、Eval 和人工 Gate
状态 当前消息与工具轨迹 持久任务状态、产物和跨次反馈
隔离 不一定具备 Worktree、容器或沙箱
交付 最终文本 PR、工单、报告、部署或其他业务结果

一个 while(true) 缺少目标、验证器、退出条件、状态恢复、幂等、隔离和人工升级机制，因此不是完整的 Loop Engineering。

“自唤醒”也不是模型凭空醒来，而是由调度器、Webhook、CI、消息队列等可信外部事件触发。

# 8. Loop Engineering 的六类组件

# 8.1 Automations

Cron、Webhook、CI 失败、Issue 创建、文件变化或消息事件触发任务，使系统从等待用户对话的 Pull 模式转向事件驱动。

触发器要去重、鉴权和限流，避免同一事件创建多个重复任务。

# 8.2 Worktrees / Sandboxes

每个任务使用独立 Git Worktree、容器或沙箱，隔离文件修改、进程、网络和凭证。并发 Agent 不能共享同一个可写工作区。

# 8.3 Skills

将“修复测试”“发布服务”“处理告警”等 SOP、脚本和资源封装为可复用 Skill。Skill 应包含触发条件、步骤、验证、禁止动作和失败处理，而不只是长 Prompt。

# 8.4 Connectors

通过 MCP、API、CLI 和数据库工具连接代码仓库、CI、日志、工单和沟通系统。Connector 提供能力，Harness 决定权限与执行策略。

# 8.5 Sub-agents

Planner、Coder、Reviewer、Tester 等子 Agent 在独立上下文中处理专业子任务。主 Agent 负责分派、依赖、结果汇总和终止，不能让子 Agent 无限互聊。

# 8.6 Memory / State

持久化目标、计划、检查点、失败模式和产物引用。没有状态的自动循环只是反复从头执行，无法恢复、去重和改进。

# 9. 实战：夜间自动修复失败测试

# 9.1 最小闭环

CI 失败或定时任务触发
-> 对事件去重并锁定目标提交
-> 创建隔离 Worktree / 容器
-> 加载项目规则和修复测试 Skill
-> 复现失败，保存基线和日志
-> Agent 制定计划并做最小修改
-> 运行目标测试
-> 运行相关回归、编译、Lint 和安全检查
-> 检查 Diff 范围与敏感文件
-> 失败诊断回填，限次修复
-> 全部通过后提交独立分支并创建 Draft PR
-> 超出能力或风险边界时交给人工

# 9.2 状态设计

任务状态至少包含：

  • 触发事件 ID、仓库、基线提交和分支。
  • 当前计划、轮次、修改文件和测试集合。
  • 已执行命令、退出码、错误摘要和产物路径。
  • Token、费用、总耗时和剩余预算。
  • RUNNING / SUCCEEDED / FAILED / NEEDS_HUMAN / CANCELLED。

# 9.3 终止与人工升级

出现以下情况应停止自动修复：

  • 达到最大轮次、时间或费用预算。
  • 多轮产生相同 Diff 或相同失败。
  • 测试疑似不稳定，无法建立可靠基线。
  • 需要修改权限、安全、支付、生产配置或大范围架构。
  • 测试通过但 Diff 超出任务范围。
  • 无法访问依赖、凭证或必要环境。

默认只创建可审核的 Draft PR，不应自动合并或直接发布，除非组织已为该类低风险变更建立明确策略和额外验证。

# 9.4 成功标准

“目标测试通过”只是必要条件，还应检查：

  • 修复前测试能够稳定复现失败。
  • 修复后相关测试和回归测试通过。
  • 没有通过删除测试、跳过断言或降低质量门槛作弊。
  • 修改范围与 Issue 一致，没有触碰禁止文件。
  • PR 描述包含原因、修改、验证和剩余风险。

# 10. Harness 与 Loop 的关系

二者重叠很大：循环检测、验证中间件、预算、Skill、Connector、Memory 和子 Agent 都可同时归入两者。

可以用不同设计尺度理解：

  • Harness Engineering：单次 Agent 执行前、中、后的运行保障。
  • Loop Engineering：完整任务从事件触发到验证交付的自治生命周期。

Loop Engineering 没有发明全新的底层机制，它重新聚焦了自动触发、隔离运行、强制验证和跨任务反馈，反映 Agent 从“被调用的工具”向“持续运行系统”的演进。

实际设计时无需争论组件属于哪个名词，只需要确认目标、状态、权限、验证、终止、恢复和责任人是否明确。

# 11. 常见误区

# 误区一：换更强模型就不需要 Harness

更强模型仍可能越权、误用工具、遗漏验证和陷入循环。运行时约束不能由模型能力替代。

# 误区二：让模型反思一次就是验证

反思仍是概率性文本生成。编译、测试、规则和真实环境检查才是主要验证依据。

# 误区三：失败就把完整日志无限塞回 Context

日志应外存，Context 只保留可操作摘要、相关片段和引用，否则会造成上下文膨胀与目标分散。

# 误区四：自动循环次数越多，结果越可靠

没有新证据和新策略的重试只会增加费用。应检测重复状态，在有限次数后换方案、降级或交给人工。

# 误区五：测试通过就可以自动上线

测试无法覆盖权限、数据迁移、业务影响和安全风险。交付策略必须匹配变更风险，默认保留人工合并或发布 Gate。

# 12. 面试速答

# 12.1 Harness Engineering 是什么？

Harness 是 LLM 外部的 Agent 运行环境，通过上下文、工具、状态、编排、外部验证、安全护栏、恢复和可观测性，让模型能力稳定、可控、可评估地完成任务。

# 12.2 Prompt、Context 和 Harness 有什么区别？

Prompt 决定怎样描述任务，Context 决定模型本轮看到什么，Harness 决定模型能力如何被执行、验证、约束和恢复。Harness 通常包含前两者，但关注范围更大。

# 12.3 为什么 Agent 不能自己验证自己？

模型可能延续生成时的错误假设，自我评价也不可证明真实结果。应优先使用编译、测试、Schema、业务规则和真实环境操作等外部验证，LLM Reviewer 只是补充。

# 12.4 Agent Loop 与 Loop Engineering 有什么区别？

Agent Loop 是单次任务内部的推理、行动和观察循环；Loop Engineering 覆盖外部触发、隔离、技能、状态、验证、重试、人工升级和最终交付，是跨会话、跨系统的生产闭环。

# 12.5 如何防止 Agent 循环失控？

设置最大轮次、总超时、Token/费用预算、重复状态检测和取消信号；工具执行使用最小权限和沙箱；失败时限次重试，涉及高风险或无法收敛时保存检查点并转人工。

# 12.6 如何评价一个 Coding Agent Harness？

不只看生成代码质量，还要看任务完成率、编译和测试通过率、回归率、工具正确率、越权率、平均轮次、成本、恢复能力、人工接管率以及最终 Diff 是否符合任务范围。
