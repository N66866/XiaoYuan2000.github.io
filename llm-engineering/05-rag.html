# RAG 检索增强生成

# 本章导读

RAG（Retrieval-Augmented Generation，检索增强生成）让 LLM 在生成答案前，先从外部知识源检索证据，再结合证据回答。它的目标不是把知识训练进模型，而是让模型在需要时“查资料再回答”。

RAG 常用于企业制度、产品手册、代码文档、客服知识库、法律医疗资料等私有或持续变化的知识。它能改善事实依据、知识时效性和私有知识覆盖，但不天然保证事实正确、权限安全或零幻觉；这些仍需要数据治理、检索策略、提示词约束、引用和评测共同保证。

先记住两条主线：

  • 离线索引构建：文档读取 -> 清洗 -> 分片 -> 向量化 -> 写入索引。
  • 在线检索生成：理解问题 -> 检索候选 -> 过滤/融合/重排 -> 构建上下文 -> LLM 基于证据回答。
flowchart LR

    B --> C["分片 Chunking"]
    C --> D["Embedding"]
    D --> E["向量库 / 关键词索引"]

    Q["用户问题"] --> T["查询转换、路由"]
    T --> R["多路检索"]
    E --> R
    R --> F["权限过滤、融合、重排"]
    F --> G["上下文构建"]
    G --> L["LLM 生成带引用的答案"]

# 1. 为什么需要 RAG

# 1.1 LLM 的知识边界

LLM 根据训练语料和当前上下文预测下一个 Token。它不自带企业内部文档、最新法规、实时库存或受权限保护的数据，也不会自动验证自己生成的内容是否真实。

RAG 通过把检索到的原文片段放入 Prompt，让模型在“有依据”的上下文中作答：

请仅根据以下参考资料回答问题。
资料中没有明确依据时，请回答“知识库中未找到可依据的信息”，不要编造。

[资料 1] ...
[资料 2] ...

问题：...

# 1.2 适用与不适用场景

场景 是否优先用 RAG 原因
企业制度、产品手册、内部 Wiki、代码文档 是 私有知识，且需要来源追溯
文档频繁更新的政策、说明书 是 更新索引通常比微调更快
产品型号、错误码、术语查询 是，建议混合检索 既要语义理解，也要精确匹配
订单余额、库存、报表统计 不应只用 RAG 应通过 Function Calling、SQL 或 API 查询权威实时数据
固定话术、输出风格、分类习惯 通常优先 Prompt 或微调 这是模型行为问题，不是外部知识检索问题
创建退款、工单等业务动作 不应使用 RAG 执行 应使用受控工具调用并做权限、幂等和审计

# 1.3 RAG、微调和工具调用的边界

技术 解决的问题 知识更新 典型产物
RAG 让回答基于外部资料 重建或增量更新索引 文档问答、知识助手
微调 改变模型风格、格式或任务能力 训练成本高，更新慢 固定格式抽取、领域表达
Function Calling 查询实时系统或执行业务动作 直接读权威系统 查订单、算价格、发起审批

面试表达：

RAG 是模型推理时的外部知识层，不是训练方式。知识经常变、需要引用或属于私有数据时优先 RAG；实时精确数据走工具或数据库；微调主要解决模型行为和输出分布问题。

# 2. 离线索引构建：数据质量决定上限

RAG 的经典原则是 GIGO（Garbage In, Garbage Out）：源文档混乱、过期、无权限标记或切分错误，后续再复杂的重排和 Prompt 也很难救回来。

# 2.1 ETL 视角

索引构建可以看作 ETL：

  1. Extract：读取 PDF、Word、Markdown、HTML、数据库、网页等来源。
  2. Transform：解析、清洗、补充元数据、分片，必要时做 OCR 或视觉识别。
  3. Load：生成向量并写入向量库、关键词索引及文档元数据表。

建议为每个 Chunk 保存至少以下信息：

字段 作用
chunkId 稳定的片段唯一标识，用于去重、删除与融合
documentId 对应源文档
text 最终提供给 LLM 的原文内容
embedding 语义相似度搜索索引
metadata 来源、页码、版本、时间、权限等
contentHash / version 增量更新与失效判断
parentChunkId 父子分片关联，可选

不同格式的读取逻辑应隔离，不要把 PDF、Word、HTML 的解析堆到一个大段 if-else 里。Java 中可按策略模式路由：

Spring AI 常用对象：

类 作用
DocumentReader 从特定来源读取内容并转成 Document

PagePdfDocumentReader 按页读取 PDF，适合页码引用或结构较差的 PDF

扫描版 PDF 没有可靠文本层时，先做 OCR 或视觉文档解析。LLM 分片不是图片解析的替代品。

# 2.3 文档清洗：删除噪声，不删除结构

常见清洗包括：

  • 去除无意义的空白、乱码、重复段落。
  • 去除跨页重复的页眉、页脚、页码、水印。
  • 统一编码、日期格式、标题层级和来源字段。
  • 识别过期文档、重复版本和无权入库内容。

不要无脑执行“删除全部换行、空格、特殊字符”：

  • Markdown 标题、列表、代码块、表格和引用是重要结构。
  • 代码知识库中，代码块通常比自然语言说明更关键。
  • 表格应保留 Markdown/HTML 表格，或转为“列名: 值”的结构化文本；不要把行列关系打散。
  • 清洗时要保留原始 metadata，否则会丢失页码、来源和权限。

# 2.4 元数据：Chunk 的身份证

元数据既服务检索精度，也服务安全与可追溯性。常见字段：

sourceUrl, fileName, page, section, product, documentVersion,
publishedAt, effectiveAt, tenantId, departmentId, roleId,
securityLevel, documentId, chunkId

2
3

它的三个核心价值：

  1. 精确过滤：例如只检索《汽车手册 2023 版》，避免语义相近的 2024/2025 版混入。
  2. 权限控制：按租户、部门、角色、密级过滤，保证未授权 Chunk 不会进入 LLM 上下文。
  3. 引用追溯：答案展示文件名、章节、页码、链接，让用户核验事实来源。

安全边界：

  • 用户 ID、租户、部门、角色、密级等过滤条件必须从登录态和授权服务中生成。
  • 不可让 LLM 决定“我有权查哪些部门资料”，也不可直接信任用户拼出的过滤表达式。
  • 模型可辅助抽取“产品型号、文档版本、日期”等业务检索条件，但必须经过白名单、格式和权限校验。

# 3. 分片：在检索精度与上下文完整性之间取平衡

# 3.1 为什么必须分片

完整文档往往超过 Embedding 和 LLM 上下文限制。即使能塞进去，大量无关内容也会降低检索精度、浪费 Token，并让模型忽略关键证据。

Chunk 太大：

  • 一个 Chunk 混入多个主题，真正相关句子被噪声稀释。
  • 向量语义不聚焦，召回分数不稳定。
  • 无关内容挤占最终 Prompt。

Chunk 太小：

  • 句子、条件、表格行或代码上下文被截断。
  • 单块缺少上下文，模型容易误解。
  • 索引数量、存储和召回重复增加。

# 3.2 常见分片策略

策略 做法 优点 风险与适用边界
固定大小 按字符或 Token 固定切分 简单、稳定、低成本 易破坏语义；适合无结构纯文本兜底
递归分片 优先按段落、换行、句号等分隔符，超长再细分 通用、工程上最常用 分隔符应适配中英文与文档格式
文档结构分片 按 Markdown 标题、HTML 节点、PDF 页/段落、章节切分 保留业务结构 依赖文档结构与解析质量
语义分片 依据句子相似度或主题变化确定边界 主题连贯性更好 需要 Embedding，阈值和语言支持需评测
LLM 分片 让 LLM 识别逻辑段落、标题和主题 可处理复杂高价值文档 成本、延迟、非确定性高，需校验

经验上，技术 Markdown 可优先按标题和段落切分；普通文本可用递归分片；扫描 PDF 先 OCR/版面解析，再做结构或递归分片。没有放之四海而皆准的 chunkSize。

# 3.3 Chunk Size 与 Overlap 如何调

chunkSize、chunkOverlap 应基于以下因素调优：

  • 文档类型：制度条款、FAQ、代码、表格、论文的语义单位不同。
  • Embedding 模型的单输入 Token 上限。
  • LLM 上下文预算和最终期望引用粒度。
  • 用户真实问题、答案标注和离线评测结果。

overlap 让相邻 Chunk 共享边界内容，能缓解句子或段落被截断的问题；但 overlap 过大将导致索引膨胀、重复召回和 Prompt 冗余。它只能补足局部边界，不等于恢复完整章节语义。

# 3.4 父子分片

父子分片同时利用“小块检索准”和“大块上下文全”的优点：

    C2 --> V
    C3 --> V

典型设计：

  • 父块：保存完整章节、表格说明或图文单元，通常放 MySQL、对象存储索引表或文档库。
  • 子块：更小、更聚焦，生成 Embedding 并存入向量库。
  • 子块 metadata 中保存 parentChunkId、标题路径、页码等。
  • 检索到子块后，按父 ID 回填父块或相关窗口，再去重并做 Token 预算控制。

它适合长章节、表格、图片说明和需要完整上下文的知识。代价是父块存储、关联查询、缓存、更新一致性、去重，以及父块过大导致 Prompt 膨胀。

# 4. Embedding、向量检索与向量库

# 4.1 向量模型与生成模型

模型 输入与输出 在 RAG 中的责任
Embedding Model 文本 -> 高维浮点向量 表示语义，用于相似度检索
Chat / LLM 问题 + 上下文 -> 自然语言 阅读证据、推理与生成回答

同一检索空间里的文档和 Query 必须使用同一 Embedding 模型、同一版本，或官方定义的兼容 query/document encoder 组合。更换模型、维度或向量空间后，旧索引通常不能直接复用，必须重新嵌入并重建索引。

# 4.2 相似度度量

度量 含义 常见场景
余弦相似度 比较向量方向，忽略长度 文本语义检索最常见
点积 衡量同方向重叠程度 归一化或特定训练目标的向量模型
欧氏距离 比较空间直线距离 有明确几何意义的向量场景

距离度量必须与 Embedding 模型和向量库配置匹配，不能只因为“余弦最常见”就盲目切换。

# 4.3 Spring AI 的核心抽象

类 作用
EmbeddingModel 文本或 Document 向量化
VectorStore 向量存储、删除和相似度检索的统一接口
PgVectorStore PostgreSQL + pgvector 的 VectorStore 实现
SearchRequest 指定 Query、topK、相似度阈值和 metadata 过滤

VectorStore 的 add(documents) 通常会执行“调用 EmbeddingModel -> 写入向量、文本、元数据”。仍需在业务侧按 Embedding API 的单次文档数量和总 Token 上限做批处理；向量库的写入批次配置不一定能限制模型请求批次。

简化检索示例：

SearchRequest request = SearchRequest.builder()
        .query(query)
        .topK(10)
        .similarityThreshold(0.65)
        // 权限和租户过滤应由后端安全上下文构造
        .filterExpression(filterExpression)
        .build();

List<Document> candidates = vectorStore.similaritySearch(request);

# 4.4 向量数据库选型

方案 优势 适用场景 边界
pgvector 复用 PostgreSQL、SQL 与权限体系，结构化过滤方便 中小规模企业知识库、已有 PG 团队 超大规模与极高并发不占优
Elasticsearch 倒排关键词和向量检索共存，便于混合检索 已有 ELK、错误码/型号等关键词强的场景 原生向量性能通常不如专用向量库
Milvus 分布式、高吞吐、多索引、面向海量向量 亿级向量、较高并发、可投入运维 部署和运维复杂
Qdrant HNSW、过滤与部署体验较好 中大型向量检索服务 仍需评估集群与生态适配
Chroma 轻量、开发快速 教学、原型、个人项目 不适合高并发和大规模生产

选型优先级通常是：权限与过滤能力、数据规模与延迟目标、现有技术栈、运维成本、混合检索需求、社区与生态，而不是只比较单次搜索速度。

# 4.5 索引算法

算法 核心思路 优点 代价
精确 KNN / Flat 比较所有向量 结果准确 数据大时计算和延迟高
IVF 先聚类，只搜索部分簇 更快、更省资源 可能漏召回，需调 nprobe 等参数
IVF_PQ IVF 后压缩向量 内存占用低，适合极大规模 精度损失更明显
HNSW 构建多层邻接图导航 高召回、低延迟、支持动态插入 建索引慢、内存高、参数需调优

生产上常用近似最近邻，是为了在可接受的召回损失下换取延迟和成本。具体选 HNSW 还是 IVF/PQ，需要在业务数据上评估，不存在“准确率差别一定不大”的结论。

# 4.6 离线模型

在线 Embedding 便于接入，但有调用成本、网络依赖和数据外发风险。内网或高敏感场景可使用本地 BGE、Ollama 或 ONNX Runtime 等离线模型。模型选择需匹配中文/多语言、维度、吞吐、GPU/CPU 资源和检索效果。

# 5. 在线检索生成：从 Query 到可信答案

# 5.1 基础 Naive RAG

最基础的在线链路：

  1. 用户提出问题。
  2. 对问题做 Embedding。
  3. 在向量库按相似度检索 TopK Chunk。
  4. 将 Chunk 原文、来源和问题组装成 Prompt。
  5. LLM 根据资料生成答案。
  6. 返回答案与引用；无证据则拒答或澄清。

基础 RAG 能快速验证价值，但生产系统往往还需要权限过滤、查询改写、混合检索、重排和评测。

# 5.2 手动编排与 QuestionAnswerAdvisor

方式 优点 适用场景
手动编排 每个阶段可控，便于插入权限、父子分片、混合检索、审计和自定义引用 生产级复杂 RAG
QuestionAnswerAdvisor 自动完成基础检索和上下文注入，代码少、复用方便 单向量库、基础问答原型

QuestionAnswerAdvisor 的大致职责：

  • before：检索关联文档，将其注入模型请求上下文。
  • after：把召回文档及其 metadata 加到响应元信息，便于记录和追溯。

注意：Advisor 省去样板代码，但不会自动解决权限、数据质量、混合检索、父子分片、复杂路由和效果评测。

# 5.3 空召回与拒答

当低于阈值或没有检索到资料时，应回答“知识库中未找到可依据的信息”，可附带澄清问题或进入明确配置的联网/人工兜底流程。

企业知识库场景中，不应静默让模型凭训练知识补全，因为它可能过期、与企业规则不一致且无法引用。空召回也应记录日志，区分“确实无资料”和“索引、过滤、解析异常”。

# 5.4 上下文构建

最终送给 LLM 的不是“所有召回文本”，而是经过筛选、排序、去重和长度控制的证据包：

  • 保留 chunkId、文档版本、页码和链接，方便生成引用。
  • 去掉重复 Chunk、相同父块和冲突的过期版本。
  • 给每个来源设置 Token 预算，避免上下文爆炸。
  • 提示模型把资料当作不可信外部内容，不执行资料中的指令，防止文档 Prompt Injection。
  • 要求“仅基于证据作答；证据不足时说明不足；列出来源”。

# 6. Advanced RAG：提升召回与排序质量

# 6.1 Metadata 过滤

向量相似度只能回答“语义像不像”，不能可靠回答“是否属于当前租户、版本是否有效、用户是否有权查看”。所以应在相似度搜索时追加后端构造的 metadata 条件：

tenantId = 当前租户
AND departmentId IN 当前用户可访问部门
AND documentVersion = 用户指定版本
AND effectiveAt &lt;= 当前时间

2
3
4

过滤必须在召回阶段由服务端执行，不能只在最终 Prompt 写“不要回答机密内容”。

# 6.2 查询转换：改写、多查询、澄清与 HyDE

技术 解决的问题 注意点
Query Rewrite 补全指代、结合历史、改写为更像文档的检索表达 改写可能曲解原意；最终生成仍以原始问题为准
Multi-Query / 查询分解 对复杂问题生成多个检索角度或子问题 候选变多，需控制成本和去重
问题澄清 日期、版本、目标对象等关键槽位缺失 应向用户追问，不要臆测关键业务条件
HyDE 先生成假设性答案文档，对其向量化后检索真实资料 假设文本仅用于检索，不能作为事实证据；增加模型调用和偏差风险

例如“它的退款规则是什么”可结合对话历史改写为“订单 X 对应商品的退款规则是什么”；若订单、商品和版本缺失且会改变结果，应先澄清。

# 6.3 查询路由与查询构造

查询路由决定查询哪个知识源或走哪条流程：

  • 产品说明、制度文档 -> 向量库。
  • 错误码、产品型号 -> 关键词/混合检索。
  • 订单金额、库存、统计 -> 关系数据库或业务 API。
  • 实体关系、多跳依赖 -> 图数据库。
  • 时效性公开信息 -> 经授权的联网搜索。

查询构造是把自然语言转换为目标源可执行的形式，例如 SQL、Cypher、ES DSL、API 参数或 metadata filter。

Text-to-SQL 的安全要求：

  • 只读数据库账号或只读副本，最小权限。
  • 表、列、行级权限白名单。
  • SQL Parser / AST 校验，只允许单条 SELECT，禁止 DDL、DML、存储过程和多语句。
  • 参数化、超时、分页和最大返回行数。
  • 审计、异常告警；不要将未经校验的模型 SQL 直接交给 JdbcTemplate 执行。

# 6.4 混合检索与 RRF

稠密向量检索擅长同义表达和语义相关；稀疏检索（BM25、Elasticsearch）擅长错误码、型号、人名、缩写和精确关键词。

混合检索通常并行执行两路或多路召回：

Query
  -> Vector Search -> 候选列表 A
  -> BM25 / ES     -> 候选列表 B
  -> 去重与融合    -> 候选集合
1
2
3
4

不同系统的原始分数通常不可直接相加。RRF（Reciprocal Rank Fusion）只依赖排名进行融合：

RRF(d) = sum(1 / (k + rank_i(d)))
1
  • 同一 Chunk 在多个列表中排名越高，RRF 得分越高。
  • k 是平滑常数，常见经验值为 60。
  • RRF 适合异构检索系统，避免复杂且脆弱的分数归一化。

RRF 是候选融合，不是 Cross-Encoder 意义上的语义重排。应使用稳定的 chunkId 去重和累积排名，再进入后续精排。

# 6.5 Rerank：从粗召回到精筛

向量检索、BM25 和 RRF 的目标是“不要漏掉可能相关的候选”，即高召回；Reranker 的目标是“把最相关的少数证据排到前面”，即高精度。

Cross-Encoder / 专用 Reranker 会同时输入 Query + Document，更细致地判断相关性：

Query
  -> 多路召回 20~100 个候选
  -> RRF / 去重
  -> Reranker 逐对评分
  -> 选 3~10 个上下文
  -> LLM
1
2
3
4
5
6

不要对全库做 Rerank：它需要逐条联合计算，成本与延迟随候选数量线性增长。Reranker 也无法找回“召回阶段完全没找回”的证据。

注意权衡：语义 Reranker 可能压低关键词命中但表述不相似的内容，尤其是错误码、型号等场景，应通过评测决定是否保留关键词权重或采用业务规则。

# 6.6 Graph RAG

传统向量 RAG 擅长检索相似段落，但面对多跳关系时容易得到碎片化上下文，例如：

“电影 A 的导演还导演过哪些电影？”
电影 A -> 导演 -> 其他电影
1
2

Graph RAG 会从文档中抽取实体和关系，构建图结构：

(电影 A) -[导演]-> (导演 X)
(导演 X) -[导演]-> (电影 B)
1
2
概念 含义
节点 人、产品、部门、服务、合同、事件等实体
边 依赖、负责、属于、导演、购买等关系
属性 时间、版本、状态、密级等
图查询 通过关系路径做 Cypher 等查询

Graph RAG 适合依赖分析、组织关系、供应链、知识图谱问答和复杂多跳推理。它通常与向量检索互补：图查关系路径，向量库查非结构化说明、长文本和模糊描述。

额外成本包括实体/关系抽取质量、图谱更新、实体消歧、图数据库运维和查询权限控制。不要因为“问题有关系词”就盲目引入图数据库。

# 7. Modular RAG：将流程变成可组合组件

Naive RAG 是固定流水线；Advanced RAG 叠加了很多优化；Modular RAG 则把查询转换、检索、重排、上下文构建、生成和后处理拆为独立组件，按场景组合。

典型模块：

  1. Query Transformer：改写、拆解、HyDE、澄清。
  2. Query Router：选择向量库、图数据库、SQL、Web 搜索等。
  3. Retriever：向量、BM25、图、数据库、Web 等多源召回。
  4. Content Aggregator：融合、去重、压缩、RRF、Rerank。
  5. Context Builder：父块回填、Token 预算、引用和 Prompt Injection 防护。
  6. Generator：调用 LLM 生成答案。
  7. Post Processor：引用标注、事实校验、格式处理、审计与反馈收集。

模块化的价值：

  • 为不同业务组合不同链路，而不是堆满一个 chat() 方法。
  • 模块可独立单测、压测、观测和替换。
  • 可逐步灰度某个 Reranker、Embedding 模型或检索策略。
  • 更便于多人协作、故障定位和 A/B 实验。

# 8. 多模态 RAG

传统文本 RAG 会忽略图片、图表、复杂表格和公式。多模态 RAG 的目标是把这些信息变成可检索、可引用的证据。

# 8.1 PDF 图文处理链路

  1. 使用 PDF 解析工具按页提取文本、图片和表格，并记录页码、坐标、来源。
  2. 对图片使用视觉模型进行 OCR、图表/公式/流程图描述。
  3. 将文本片段与图片描述按原始阅读顺序合并；图片保留 URL、页码、坐标等 metadata。
  4. 将统一内容做结构化分片、Embedding 和索引。
  5. 检索命中图片相关内容时，回答附带图片/页码来源；必要时让多模态模型直接参与最终理解。

例如使用 PDFBox 可提取 PDF 文本与图片；使用支持图片输入的 ChatModel / UserMessage 调用视觉模型得到图片描述。关键不是“把整页丢给模型总结”，而是尽量保留图文位置、顺序、来源与可核验的原始素材。

# 8.2 收益与风险

收益：

  • 图片、图表、扫描件、公式和表格中的信息可以进入检索范围。
  • 用户可以询问“图中告警流程是什么”“该仪表盘趋势如何”等文本 RAG 难以覆盖的问题。

风险：

  • OCR 和视觉模型可能错读文字、数字、坐标或图例，甚至产生幻觉。
  • 图片描述会丢失空间关系和部分精确数值。
  • 图像处理增加成本、延迟、限流与重试复杂度。
  • 图片外发可能触及隐私、版权和合规边界。
  • 图文顺序错配、图片更新后描述未重建，会造成错误引用。

高风险场景应保留原图、页码和可访问链接；对关键数字、医学影像、合同图表等内容建立人工复核或专门模型校验。

# 9. 索引更新、权限与可观测

# 9.1 增量更新与幂等

文档更新、撤销、删除或权限变化后，索引必须同步：

  1. 以稳定的 documentId 标识源文档。
  2. 用 contentHash、版本号或更新时间判断是否变更。
  3. 删除或失效旧版本的所有 Chunk 和关键词索引记录。
  4. 重新读取、分片、嵌入并 Upsert 新 Chunk。
  5. 权限变化时更新 metadata / ACL；是否重嵌入取决于内容是否改变。

“设置处理中状态”不足以保证幂等。应结合唯一约束、任务幂等键、分布式锁或消息去重、Upsert、失败重试和可恢复任务状态。分片策略或 Embedding 模型变更时，通常需要全量重建对应索引版本。

# 9.2 观测什么

至少记录并可关联：

  • 请求、用户权限上下文、路由结果和过滤条件。
  • 改写前后 Query、召回来源、候选数、分数、RRF/Rerank 排名。
  • 选入 Prompt 的 Chunk ID、版本、页码和 Token 数。
  • 模型回答、引用、拒答原因、延迟、Token、Embedding/Rerank 成本。
  • 索引任务的文档版本、成功/失败 Chunk 数和重试原因。

注意日志脱敏：不要把机密原文、用户隐私、Access Token 或完整权限数据直接输出到普通日志。

# 10. RAG 评测与优化顺序

不要仅凭“模型回答看起来不错”判断 RAG 有效。建立包含真实用户问题、期望答案、关键证据 Chunk/文档和权限场景的小型评测集，再逐步扩大。

维度 关注指标
召回质量 Hit Rate、Recall@K、MRR、NDCG、关键 Chunk 是否命中
上下文质量 Context Precision、Context Recall、重复率、Token 占用
生成质量 正确性、事实忠实度、答案相关性、拒答正确性
引用质量 是否可定位、是否支持结论、是否引用过期版本
工程指标 P95 延迟、吞吐、Token、Embedding/Rerank 成本、索引时长
安全指标 未授权内容零召回、敏感字段脱敏、权限变更生效时延

RAGAS 等工具可以辅助自动评测，但不能替代人工抽检。尤其是高风险领域，应使用已标注的真实问题和专家审核。

推荐优化顺序：

  1. 先治理数据源、权限和文档版本。
  2. 确定适合业务的分片与 metadata。
  3. 建评测集，调 Embedding、TopK 和阈值。
  4. 再加入混合检索、RRF、Rerank、父子分片等复杂能力。
  5. 最后根据复杂关系或图文资料，评估是否引入 Graph RAG、多模态 RAG。

不要在基础索引质量很差时先堆 HyDE、Graph RAG 或多 Agent；那只会让问题更难定位。

# 11. 常见误区

误区 更准确的理解
RAG 能彻底消除幻觉 RAG 只能提供证据，仍可能检索错、理解错或忽略证据
向量检索就是 RAG 向量检索只是常见检索手段，RAG 还包括索引、过滤、上下文与生成
Chunk 越小越精准 太小会失去语义上下文，召回和生成都可能变差
所有文档都应删除换行和代码块 应删除噪声、保留有业务意义的结构
只靠 Prompt 约束权限即可 权限必须在检索前由后端强制过滤
RRF 就是 Rerank RRF 融合多个排名；Reranker 对 Query-Document 做语义精排
Reranker 越强越好 需权衡召回数、延迟、成本和关键词精确性
HyDE 生成的内容可以当证据 HyDE 仅用于构造检索向量，事实证据必须来自真实文档
用 LLM 生成 SQL 后直接执行 必须限制账号权限、校验 AST、限制范围并审计
空召回时让模型自由回答体验更好 企业知识库里这会制造不可追溯的错误，应拒答或走显式兜底

# 12. 面试速答

# 什么是 RAG？

RAG 是检索增强生成。它先从外部知识库中检索与用户问题相关的证据，再把证据和问题一起交给 LLM 生成回答。它适合私有、频繁变化且需要引用的知识，核心包含离线索引构建和在线检索生成两条链路。

# 如何提升 RAG 效果？

我会先保证数据源、文档结构、分片和 metadata 的质量，并建立评测集。在线侧再按问题引入权限过滤、查询改写、混合检索、RRF 融合、Rerank、父子分片和上下文压缩。优化目标不是只提高相似度，而是同时提升关键证据召回、答案忠实度、引用准确性、延迟和安全性。

# 如何做企业级 RAG 权限控制？

把租户、用户、部门、角色、密级和文档状态写入 Chunk metadata；请求进入时从认证授权系统取得访问范围，并作为向量检索/关键词检索的强制过滤条件。未授权内容不能被召回，更不能进入模型上下文；Prompt 约束只能作为补充，不能替代服务端 ACL。

# RAG 中为什么需要混合检索与重排？

向量检索理解语义但对型号、错误码等精确术语不稳定，BM25 擅长精确匹配但不理解同义表达，所以先并行召回并用 RRF 等方法融合。然后用 Reranker 对较小候选集做 Query-Document 精排，把最有证据力的内容给 LLM，兼顾召回率、精度和上下文成本。

# RAG 什么时候考虑 Graph RAG 或多模态 RAG？

当问题依赖实体关系和多跳推理，例如依赖链、组织关系、供应链时，评估 Graph RAG；当关键知识存在图片、表格、图表、扫描件或公式中时，评估多模态 RAG。两者成本和工程复杂度都更高，应建立在基础 RAG 数据质量和评测已经稳定的前提上。
